Six primitives. That is the whole API.

Each one is a function in the client and a row in your database.

  • enqueue()

    Enqueue a job

    Insert a job in the same transaction as the data it depends on.

    0.9 msmedian insert

  • schedule()

    Schedules

    Cron syntax, time zones, and no double runs when two workers wake at once.

    1 sresolution

  • retry

    Retry policies

    Exponential backoff with jitter, a cap, and a dead-letter table.

    25max attempts

  • batch()

    Batches

    Fan out ten thousand jobs and get one callback when the last finishes.

    10kjobs per batch

  • CLI

    runnel dev

    A local worker that reloads on save and prints every run.

    4default concurrency

Migrating from a Redis queue is a small diff.

The client keeps the shape you know. What changes is where the job lives: in the same transaction as the order that caused it.

  • No job without its row, no row without its job
  • Drop one service from your stack
  • Keep your existing worker code

From install to production in three steps.

  1. Define a job

    A job is an exported function in ./jobs. Its file name is its name.

    export default async function receipt({ id }) {  await mail.send("receipt", id);}

  2. Enqueue it in a transaction

    Pass the transaction you already have. If it rolls back, the job never existed.

    await runnel.enqueue(tx, "receipt", { id });

  3. Run workers where your app runs

    Same container, a separate process, or our hosted workers. They coordinate through Postgres advisory locks.

    runnel work --concurrency 16✓ 16 slots · 5 queues

Questions

Not here? Ask in a support request.

Will it slow down my main database?

A busy queue adds a few hundred small writes per second. Most teams start on their main instance and move queues to a replica of their own when they pass 5,000 jobs per second.

What happens if a worker dies mid-job?

Its lock expires after the job's timeout and another worker picks the job up. The attempt is recorded as abandoned.

Can I read the jobs with plain SQL?

Yes. They are rows in runnel.jobs. The schema is documented and stable within a major version.
